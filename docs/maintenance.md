# Keeping the seed and the engine current

Two things in this repository go stale in different ways, and they are maintained
differently. Mixing them up is how a repository ends up either publishing memory
nobody reviewed or shipping an engine nobody updated.

## The seed (live data)

`seed/` is a snapshot of a memory that lives on a machine: a Hindsight bank and a
Sedna knowledge base. It is regenerated by

```bash
tools/refresh-seed.sh              # regenerate, run the gate, stop
tools/refresh-seed.sh --push       # ... then propose it on a branch
tools/refresh-seed.sh --dry-run    # show what would happen
```

The script refuses to run on a dirty tree, and it refuses to publish anything the
gate rejects. With `--push` it commits on `seed/refresh-<date>`, pushes that branch,
and opens a pull request with `gh` when available. **It never commits to the default
branch**: the seed is data, and data that leaves a pentest machine gets a human
before it becomes public.

### Running it on a timer

On the machine that owns the memory (Linux, systemd user session):

```bash
mkdir -p ~/.config/systemd/user
cat > ~/.config/systemd/user/sedna-seed-refresh.service <<'EOF'
[Unit]
Description=Regenerate the Sedna/Hindsight seed and propose it on a branch
After=network-online.target

[Service]
Type=oneshot
WorkingDirectory=%h/path/to/sedna-dsh
ExecStart=%h/path/to/sedna-dsh/tools/refresh-seed.sh --push
EOF

cat > ~/.config/systemd/user/sedna-seed-refresh.timer <<'EOF'
[Unit]
Description=Weekly seed refresh

[Timer]
OnCalendar=weekly
Persistent=true

[Install]
WantedBy=timers.target
EOF

systemctl --user daemon-reload
systemctl --user enable --now sedna-seed-refresh.timer
```

`Persistent=true` means a missed run happens on the next boot rather than being
silently skipped. Check what it did with
`journalctl --user -u sedna-seed-refresh.service`.

Environment overrides the script honours:

| Variable | Meaning |
|---|---|
| `HINDSIGHT_ADMIN` | path to `hindsight-admin` (auto-detected otherwise) |
| `HINDSIGHT_API_DATABASE_URL` | which embedded instance holds the bank; read from the running daemon when unset |
| `HINDSIGHT_UNIT` | unit name to read that URL from |
| `SEDNA_KB_ROOT` | knowledge base to pack (auto-detected otherwise) |
| `SNAPSHOT_EXTRA_HOME_USERS` | further home directories to normalise out of the export |
| `SNAPSHOT_EXTRA_REDACT` | regular expressions to redact on top of the built-in classes |

## The engine (source)

`engine/` and `plugin/` are vendored from
[`titagram/sedna`](https://github.com/titagram/sedna). There is no automatic
updater on purpose: vendoring means someone decides, in a reviewable commit, that a
new revision is what this stack should ship.

```bash
# from a checkout of the upstream repository
rsync -a --delete --exclude '__pycache__' --exclude '*.pyc' \
      src/sedna/ /path/to/sedna-dsh/engine/src/sedna/
cp pyproject.toml README.md /path/to/sedna-dsh/engine/
```

Then run these before committing:

```bash
tools/check-engine-drift.sh /path/to/the/upstream/checkout   # expect: no drift
tests/run-all.sh                                             # expect: all checks passed
```

and update the revision table in `engine/VENDORED.md` in the same commit — a vendored
copy whose provenance is not recorded is a fork nobody knows they are maintaining.
`tools/check-engine-drift.sh` prints the upstream revision it compared against, exits
non-zero on any difference, and works with either an upstream checkout or a tree that
already contains `src/sedna`.

Two rules:

* **never** vendor `tests/` — upstream's suite contains flag-shaped literals in its
  fixtures (it tests flag detection), so shipping it would mean either failing this
  repository's own gate or teaching the gate an exception for its own code;
* **never** vendor `raw_src/` or any collected write-ups. `.gitignore` says why.

Record what changed and why in `docs/decisions.md` when the vendored revision moves.

## What has been measured

Not everything here is theoretical, and it is worth knowing which half is which.

| Claim | How it was checked | Result |
|---|---|---|
| The published seed restores | `hindsight-admin import-bank` of the committed archive into a brand-new embedded instance | 864 documents, 13 766 facts, 8 961 observations, 7 mental models, 8 knowledge pages, 0 skipped, 9m42s |
| It restores across a version jump | the same archive imported by `hindsight-api-slim==0.10.1` (the exporter was 0.9.1), into another fresh instance | identical counts, 0 skipped, 11m20s; the archive is not tied to the version that wrote it |
| The restore needs no network for models | `HF_HUB_OFFLINE=1` during that import | succeeded; the embedding models came from the local cache |
| The installer works on an empty machine | `./install.sh` as a non-root user in a `node:24-bookworm` container with no `python3-venv` and an unwritable global npm prefix | exit 0; 95 bundles, engine 0.2.0 importing, plugin row written; `verify` 8 passed / 2 skipped |
| The gate works | 24 assertions, including scans of the real seed material, in both directions | green |
| The seed is intact and complete | `tests/test_seed_structure.sh` + `tools/verify-manifest.py` (also against a tampered copy) | green; tampering refused |

Still unmeasured: a full install on macOS, if that platform is ever supported; and a
restore into a bank that already exists, which the tooling refuses by design (import
restores a whole bank, it does not merge).

### The Hindsight install, measured piece by piece

`hindsight-all` is the right thing to install and it is **large**: it brings the local
embedding stack, and on this machine the resulting virtualenv is 6.9 GB (torch, CUDA
build). Measured in a clean `node:24-bookworm` container with a warm pip cache:

| What was tried | Time | Size | Outcome |
|---|---|---|---|
| `hindsight-api-slim[embedded-db,local-onnx]==0.10.1` | ~50 s | 1.3 GB | installs; embeddings work with `HINDSIGHT_API_EMBEDDINGS_PROVIDER=onnx` (the model is fetched from Hugging Face) |
| the same, importing the seed | — | — | **fails**: the reranker still uses the `local` backend and demands `sentence-transformers` |
| `hindsight-all==0.9.1` (what the installer pins) | — | ~6.9 GB on this machine | the supported path; the seed imports under it (verified twice, see above) |

So a torch-free install looks reachable — set the embedding **and** the reranker provider
away from `local` — but it was not verified, and the installer does not pretend
otherwise: it pins the supported path and prints the expected download size before
starting. Anyone who wants the small install should expect to choose both providers and
test the result.

The container also reproduced, on a fresh Debian, the `ensurepip` failure that
`make_venv` exists to work around — which is why that fallback is in the installer and
not in a note.

Measured on an empty `node:24-bookworm` host, as a normal user: `hindsight-all==0.9.1`
installs in **3m30s** into **6.8 GB** (it does bring `sentence-transformers`), and the
seed then imports cleanly — `EXIT=0`, **865 documents, 13 772 facts, 8 965 observations,
7 mental models, 8 knowledge pages** — with the whole embedded-database migration chain
applied from scratch. This is the last step that had never been watched completing on an
empty host; it has been now.

Run as root instead, the same host fails — `RuntimeError: Failed to start embedded PostgreSQL ... initdb:
error: cannot be run as root`. That is Hindsight's embedded database refusing a root
user, not a defect of the seed, and it is why `step_hindsight` now refuses to run as
root **before** the download instead of after it: as root the step cannot succeed, and
the error the user would otherwise see comes from inside somebody else's tool.

## The knowledge base seed: what must be in it, and why

Packing the *readable* part of the knowledge base is not enough. Two things look like
state and are in fact load-bearing:

* **`quarantine/` and `semantic_quarantine/`** — a source with no semantic bundle is
  valid only if its quarantine record says so. Ship the manifest without the record
  and the source reads as corrupt.
* **sources promoted from an engagement journal** — they reference a physical artifact
  under `engagements/`, which this seed must never publish, because it quotes what was
  found on target. Such a source is valid only while that artifact exists, so those
  sources (two, at the time of writing) are excluded by name.

Both matter because the repository is fail-closed: **one** invalid source makes the
whole canonical corpus invalid, and then every retrieval answers
`no_applicable_knowledge` — which reads exactly like "this base has nothing about your
target". A seed that ships in that state is worse than an empty one, because it looks
right.

`tools/snapshot-seed.sh` excludes the journal-promoted sources via
`tools/list_journal_promoted.py`, and the quarantine trees are packed with the rest.

A third rule once lived here and was wrong: sources whose bundles merely *matched* a
sensitive-looking pattern were excluded too, which cost three of them — one for a target
username that looked like an e-mail (`ben@silentium.htb`) and one for an address a
challenge attributes to an attacker. Excluding a source is expensive: it removes the
finding, not just the exposure. The exclusion list now comes from a predicate narrow
enough to mean something (`tools/list_seed_unsafe_sources.py`, which imports it from the
sanitizer), and on the current corpus it matches nothing. See `docs/decisions.md` D18.

`tests/test_seed_kb_audit.sh` is the check, and it runs in CI: it unpacks the seed,
audits the canonical corpus, rebuilds the retrieval index from it, asks it a question
that must return candidates, and asks it one that must be refused with empty lanes. It
does not read the seed, it uses it — which is the only way this class of bug shows up.

Finally, the seed carries no **retrieval index** on purpose — it is disposable and
rebuilt from the canonical bundles. Until it is rebuilt the lanes are empty, so the
installer builds it as part of the knowledge-base step.
